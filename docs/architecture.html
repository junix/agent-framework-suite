产品介绍

Agent Framework Suite 是一个封闭式（hermetic）跨语言一致性测试套件。它同时驱动 Python agent-framework 和 Rust agent-framework-rs 两个工作流运行时库，用同一组用例分别调用各自的公开 API，把结果归一化成标准 JSON 观测值，再逐字段比对——两个实现必须输出完全一致，才算通过。

这套件服务两种人：一是框架开发者，在改了路由逻辑或检查点机制之后跑一遍 just check，就能确认 Python 和 Rust 两端没有分叉；二是集成工程师，想知道"换语言后行为一不一样"——答案由这 10 个用例保证。

套件本身用 Go 写成一个 CLI，不实现任何工作流逻辑——路由、检查点、迭代控制全部来自被测库。它只做三件事：选用例、调驱动、比结果。所有测试在隔离子进程里完成，不访问网络，不依赖外部服务，30 秒超时兜底。

功能与特性

  • 双端强制参与 — Python 和 Rust 两个驱动都是必选的；少一个就是基础设施错误，不是跳过。
  • 10 个覆盖用例 — 从基础链式执行到检查点恢复、请求原子性，覆盖 workflow-core/v1 契约的全部公开能力。
  • 归一化观测 — 生成的 ID、时间戳、原生异常拼写等不稳定字段由驱动层抹平，只保留可比对的稳定信号。
  • Oracle 验证 + Parity 检查 — 每个用例先对各自的观测值做 oracle 校验，再把两个观测值做逐字段等价比较。
  • 封闭执行环境 — 驱动在临时 HOME、固定 PATH、UTC 时区的子进程中运行，输出限制 64KB，不碰网络和凭据。
  • CLI 四命令 — doctor 检查就绪状态，list 列出用例，run 执行测试，version 打印版本。
  • JSON 报告 — --json 输出机器可读的完整报告，包含合约版本、参与者版本、逐用例结果和重跑命令。
  • 流式输出 — --stream 把完成的用例逐条写到 stderr，方便长时间运行时观察进度。

架构总览

Agent Framework Suite 是整个系统的核心——一个 Go CLI，内含用例目录（10 个必过场景）、验证器和报告生成器。用户通过 just check 或 agent-framework-suite run 发起测试。套件把每个用例翻译成 run CASE_ID 命令，分别发给 Python 和 Rust 两个驱动子进程。驱动调用各自框架的公开 API 产生 归一化观测，套件收到后先对各自的观测做 oracle 校验（预期 outcome 是否匹配），再把两个观测做逐字段 parity 比对。底层的 Python agent-framework 和 Rust agent-framework-rs 是被测对象——套件本身不实现任何工作流逻辑。

主走查：一次 just check

下面走一遍 just check 的完整路径——从敲命令到看到 PASS，经过 6 个环节。

等待进场…

① 编译 — just check 先编译 Go 套件二进制和 Rust 驱动。Python 驱动是脚本，不需要编译。

② doctor — 套件向两个驱动各发一次 version 命令，确认它们都在、能响应、身份匹配。任何一方超时或身份不一致，退出码 3。

③ 驱动子进程 — internal/suite/runner.go 遍历用例目录（catalog.go 里的 10 个 WF-NNN），对每个用例分别调用两个驱动的 run CASE_ID。子进程在临时 HOME、固定 PATH、UTC 环境中运行，30 秒超时。

④ 收集观测 — 每个驱动把框架的返回值包装成 workflow-core/v1 标准 JSON（包含 outcome、terminal_state、outputs、requests、checkpoints、error、evidence），写到 stdout。套件通过 client.go 的 decodeOne 解码，输出限制 64KB。

⑤ 验证 — runner.go 的 ValidateObservation 先把每个观测与目录里的 Expected 做 reflect.DeepEqual（oracle 检查）。两个观测都通过后，Equivalent 做 parity 比对：去掉 participant 字段，剩余必须逐字节一致。

⑥ 报告 — 全部用例跑完，CLI 输出 passed/failed/total 摘要。JSON 报告包含每个用例的参与者结果、parity 状态、proof 字段和重跑命令。退出码 0 表示全部通过。

组件视图

CLI 层由 main.go 组成，负责解析 --python-driver 和 --rust-driver 路径、分发 doctor / list / run / version 四个子命令、控制 JSON 输出和退出码。退出码 0/1/2/3 分别对应全通过、有失败、参数错误、驱动缺失。Suite 层是业务核心：catalog.go 定义了 10 个用例及其 Expected 观测值，selector.go 支持按 ID、名称前缀、标签筛选用例，runner.go 遍历选中的用例并对每个用例调用两个驱动、验证结果、做 parity 比对。Driver 层把子进程管理封装在 client.go 里：创建临时 HOME 目录、设定固定环境变量、限制输出 64KB、从 stdout 解码恰好一个 JSON 对象。隔离子进程边界以下是两个原生驱动——Python 驱动是脚本，Rust 驱动是编译好的二进制——它们各自调用框架的公开 API，不实现任何工作流逻辑。

数据流：一个用例的生命周期

数据流的主路径是横向的四步：选中用例 → 启动两个子进程 → 调用各自框架 → 产出 JSON 观测。观测被送回 Suite 层后走两条验证路径：纵向先过 oracle——把观测与 catalog.go 里预定义的 Expected 逐字段比对；然后过 parity——把 Python 和 Rust 的观测各去掉 participant 字段后做等价比较。两条路径都通过，CaseResult 标记 passed；任何一条失败，proof 字段记录具体差异。每个子进程在同一隔离环境（临时 HOME、固定 PATH、UTC 时区、64KB 输出限制）中运行，确保观测不受宿主机配置影响。

架构特征与取舍

套件不实现工作流逻辑

驱动只翻译用例参数、调用框架 API、包装返回值。路由、检查点、迭代控制全部来自被测库——这保证了测试的保真度：如果框架行为变了，观测值一定变。

归一化只抹不稳定字段

生成的 UUID、时间戳、原生错误类名由驱动抹平，但 outcome、terminal_state、outputs 等业务信号保留原样。这避免了"归一化把真正的差异也抹掉"的风险。

封闭式环境强制隔离

子进程的 HOME 是临时目录、PATH 固定、时区锁 UTC、输出限 64KB。这套约束消除了"本地环境导致结果不同"的一整类歧义，代价是不能测试需要网络或凭据的场景。

Parity 是逐字段 DeepEqual

不做模糊匹配或阈值比较——两个观测必须在去掉 participant 字段后逐字节一致。这比"大致相同"严格得多，但跨语言兼容性需要这种确定性。
